## 3. Operating Model: Wave 1 Selection

### Why only 2 worktrees in wave 1

One human merger. Each worktree produces a branch that needs code review, metrics verification, and manual merge. Three parallel worktrees means three simultaneous reviews landing at the same time. Two is the practical maximum.

More importantly: **retrieval is the gating factor for everything downstream.** Oracle extraction at 28% on a good-retrieval subset means extraction is not the bottleneck — retrieval is. Improving extraction before retrieval is stable is wasted work.

### Workstream A — Retrieval Reranking (highest leverage)

**Why**: recall@10 = 27.6% against gold tables (file-level 62.2%). The gap between file recall and table recall means the right file is being retrieved but the right table within the file is not ranking in top 10. The reranker at `retrieve_v2.py:1394-1440` is the active target. A probe-based row/year intersection score exists (`probe_stats`) but is being added to an already-normalized FTS+metric score rather than used as a primary signal.

**Who**: Codex CLI. Mechanical tuning job — move constants, add a row-hit probe as a pre-filter, run `eval_retrieve.py` after each change.

**Reviewer**: Gemini CLI for independent second-opinion.

**Files**: `retrieve_v2.py` and `tests/test_retrieval.py` only. Do not touch `solve.py`.

**Measurable**: `eval_retrieve.py` prints recall@5/10/20/30/50 and writes `retrieve_eval.jsonl`.

### Workstream B — Eval Harness Hardening (measurement prerequisite)

**Why**: current baseline has no row-hit recall metric, no ingestion reconciliation report, and no reproducible offline smoke test. Without row-hit recall, any retrieval improvement might push file-recall up while row-recall stays flat.

**Who**: Codex CLI (second instance in a different worktree).

**Reviewer**: Claude.

**Files**: `eval_retrieve.py`, `eval_extract_oracle.py`, `batch_test.py`, `tests/test_baseline_metrics.py`, `baseline_metrics.json`. Do not touch `retrieve_v2.py`, `solve.py`, `extract.py`.

**Measurable**: eval scripts emit row-hit recall; `tests/test_baseline_metrics.py` passes with new metric keys; `baseline_metrics.json` refreshed.

### Wave 2 (after wave 1 merges)

Decompose (Claude) and fast-path (Codex) in parallel. Both touch `solve.py` — if you define precise line-range boundaries before spawning, they can work on disjoint slices. Define the boundary when you write the wave 2 task specs.

## 4. Concrete First-Ticket Specs

### Ticket A: Retrieval Reranking

```
GOAL:
  Improve retrieve_v2.py reranking so that row-level recall@10 increases
  measurably versus baseline (file-level recall@10 = 62.2%, table-level
  recall@10 = 27.6%).

BACKGROUND:
  The reranker at lines 1393-1441 of retrieve_v2.py computes a weighted sum:
  FTS score (0.75) + metric score (0.25) + probe_stats bonus + title bonus
  + file_year bonus + period bonus. The probe_stats bonus (lines 1402-1412)
  rewards tables whose best matching row has the most non-null cells.
  Currently gated on matching_rows > 0 which depends on whether row_hint
  produces any slug match. Many row_hints do not produce slug matches even
  when the correct table is in the union.

HYPOTHESIS TO TEST:
  Two targeted changes:
  1. Add a fallback probe: when row_hint produces zero slug matches
     (matching_rows=0), run a broader FTS5 probe over table_rows.row_path
     within that table using the row_hint as a MATCH query. Add any
     non-zero result as a weak bonus (0.3 scale instead of 1.2).
  2. Boost the file_year bonus weight from 0.12 to 0.18 for questions
     where year_mode is 'calendar' AND the spec has a single year.

IN SCOPE:
  retrieve_v2.py, tests/test_retrieval.py

OUT OF SCOPE:
  solve.py, extract.py, find.py, build_ledger.py, compute.py, verify.py.
  Do not modify ledger.sqlite or decompose_eval.full.jsonl.
  Do not change the FTS channel or metric channel query logic.
  Only change the reranker block (lines ~1393-1441).

COMMANDS TO RUN:
  uv run pytest tests/test_retrieval.py -x -q
  uv run python eval_retrieve.py

ACCEPTANCE CRITERIA:
  - tests/test_retrieval.py: zero regressions
  - eval_retrieve.py recall@10 >= 62.0% (baseline 58.1%, 2026-04-11)
  - eval_retrieve.py recall@5  >= 47.0% (baseline 42.7%)
  - eval_retrieve.py recall@20 does NOT decrease below 74.0% (protect the tail)
  - No single question's retrieval rank gets worse by more than 5 positions
  - No new LLM calls added anywhere in the code path

RETURN FORMAT:
  Before/after summary lines from eval_retrieve.py output.
  Exact lines changed in retrieve_v2.py with one-line rationale each.
  Any hypothesis that did NOT pan out and why.
```

### Ticket B: Eval Harness Hardening

```

IN SCOPE:

OUT OF SCOPE (explicit):

  ledger.sqlite (read-only; do not rebuild)

  (only add new keys).

COMMANDS TO RUN:
  uv run pytest tests/test_baseline_metrics.py -x -q
  uv run python eval_retrieve.py

ACCEPTANCE CRITERIA:
  - eval_retrieve.py prints a new line: "row_hit_recall@10 = X/N (Y%)"
  - baseline_metrics.json gains key "row_hit_recall_at_10" with numeric value
  - Existing file-level recall numbers unchanged or updated (whichever is more current)
  - tests/test_baseline_metrics.py passes and verifies new key exists
  - Row-hit check logic makes no LLM calls
  - Total runtime of eval_retrieve.py does not increase by more than 20%

RETURN FORMAT:
```

## 7. Risk List

### Risk 1: ledger.sqlite write contention (HIGH / EASY to prevent)

Both wave-1 agents must not write to the ledger. Read-only symlinks via `chmod 444` prevent accidental writes.

### Risk 2: agents claiming victory on stale metrics (HIGH)

Agents will run the eval script and report its output as the acceptance result. If `eval_retrieve.py` has a bug that inflates numbers, the agent will declare success on a fake improvement. **Verify eval output format yourself before spawning.** Compare line-by-line after the agent returns.

### Risk 3: retrieve_v2.py fallback probe hurts latency (MEDIUM)

FTS5 probes over `table_rows.row_path` for every table with zero slug matches could multiply query count. Mitigation in ticket: runtime increase <20%. If exceeded, gate the probe tighter.

### Risk 4: decompose.py confusion (HIGH without the warning comment)

Agents will see `decompose.py` and think it's the active decompose module. Add the warning comment yourself before spawning.

### Risk 5: wave 2 solve.py merge conflict (HIGH without boundary enforcement)

`solve.py` is 1535 lines with interleaved sections. Two agents editing "different" sections will still conflict on context lines in a squash merge. Mitigation: merge one wave-2 branch before spawning the second, OR define boundary commits and verify with `git diff main...agent/<name> -- solve.py` before merge.

### Risk 6: eval_extract_oracle.py is not deterministic (MEDIUM)

Oracle accuracy varies 3-5 points between runs on the same 50 questions. Never use oracle accuracy as sole acceptance criterion. Use retrieval recall (deterministic, cached specs) as primary gate.

### Risk 7: eval harness agent regenerates decompose_eval.full.jsonl

641 KB file looks like a generated artifact. If the agent regenerates it, retrieval eval will use different specs and before/after comparison is invalid. Explicitly listed in OUT OF SCOPE of Ticket B.

### Risk 8: agent confuses files.db with ledger.sqlite (LOW / HIGH impact)

There is a `files.db` (2.27 GB) alongside `ledger.sqlite` (2.75 GB). Any vague "use the database" instruction might query the wrong one. Task specs use explicit file paths everywhere.

### Risk 9: ingestion work invalidates retrieval improvements

If you run ingestion improvements (PLAN.md phases 1-2) before wave 1 retrieval merges, you'll need to rebuild `ledger.sqlite` and re-measure baseline. Ingestion is wave 3, not wave 1.
